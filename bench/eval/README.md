# Eval set

`queries.jsonl` — the retrieval eval, generated by `build_eval.py` (edit the
generator, not the JSONL). Regenerate: `python3 eval/build_eval.py`.

## Why style is the bucket (not "exact-symbol vs semantic")

The target user knows nothing about ffmpeg flags — they never type `-crf` or
`scale=`. So the eval stratifies by **phrasing style** of the same clueless
intent: `neutral` (well-written) / `verbose` / `terse` / `typo` / `wrong_terms`.
That directly tests the decisions we care about: does a static encoder survive
typos and wrong words, or does a transformer's subword tokenizer win there.

## Record fields

| field | meaning |
|---|---|
| `id` | `{intent}-{style}-{n}` |
| `intent` | base intent (labels are defined once per intent in `build_eval.py`) |
| `style` | bucket: neutral / verbose / terse / typo / wrong_terms |
| `media` | what the user uploaded (video/audio/image) |
| `text` | the actual query string |
| `targets` | anchors in the `all` corpus that count as a hit (**any-of**) |
| `answerable_in_cli` | is a correct chunk present in the CLI-only corpus? |
| `no_answer` | ffmpeg can't do it; system should retrieve nothing useful + abstain |
| `gloss` | human note on the intent |

## How metrics use this

- **recall@k** = a query is a hit if **≥1 of `targets`** is in the top-k. Reported
  at two k budgets (tight in-browser / generous external).
- **Coverage ceiling vs retrieval recall** = split every table by corpus. For the
  `cli` corpus, only `answerable_in_cli` queries *can* be hits — the rest measure
  the coverage gap, NOT retrieval quality. `answerable_in_cli` mechanic: cli has
  command mechanics (`-ss`/`-t`/`-an`/`-vn`/`-frames:v`) but not encoder/filter
  *names* (libmp3lame/libx264/crop/palettegen), so name-dependent intents are
  `all`-only.
- **no_answer** queries score inverted: success = retrieving nothing above a score
  threshold (don't feed confidently-wrong context to a weak reader).
- **Bootstrap CIs** on recall — with 40 queries, treat rankings as provisional and
  grow the set only where CIs overlap on a decision-relevant comparison.

## Current set (v0.1.0)

40 queries / 12 intents. Style: neutral 12, verbose 7, terse 7, typo 6,
wrong_terms 8. no_answer: 3. answerable_in_cli: 10; all-only: 27.

**Caveat (known):** these are author-written and may lexically echo the docs. Mix
in genuinely user-sourced phrasings before treating lexical-config wins as real.
Thin buckets (typo/terse/no_answer) are qualitative failure-spotting at this size,
not statistically powered.
