In-browser ffmpeg command planner — which docs-retrieval config best feeds an LLM. Updated 2026-06-22 05:34 · 37 real queries + 3 no-answer · bootstrap 2000× 95% CI.

Verdict

78% recall@20

bge-small + BM25 (RRF) on the Examples-glued corpus. The biggest lever was chunk content (gluing each ffmpeg filter's Examples into its page), not the embedding model. POTION (static) is ~30–80× faster to encode but trails on recall; BM25 alone collapses on re-worded queries.

How to read this

Corpus
cli = the ffmpeg CLI page (41 sections). all = the full manual (1590). all-glued = full manual with each filter's Examples merged into its page (1333) — the winning corpus.
Config
model × precision × fusion, on a corpus. The unit we rank.
recall@k — the boss metric
A query passes at k if ≥1 of its hand-labeled target doc sections is in the top-k retrieved (any-of). recall@k = fraction passing. k=5 = tight (small in-browser reader budget); k=20 = generous (big external reader). Retrieval feeds an LLM, which tolerates extra/misordered context — it just needs the right doc present. No human reads a ranked list, so rank order matters little.
Coverage
fraction of queries whose target even exists in that corpus — the ceiling recall can't beat. cli coverage is only 27%, which is why it can't work no matter the model.
RRF hybrid
fuse the dense (embedding cosine) and BM25 (keyword) rankings by reciprocal rank. Scale-free and robust on a small eval set.
nDCG@5
a rank-quality tiebreaker (rewards ranking the right doc higher). Not the optimization target.
95% CI
we resample the 37 queries 2000× to show uncertainty. With so few queries, treat differences inside overlapping CIs as ties.
Speed
query ms/text = runtime cost per user query (what users feel). manual ms/chunk = build-time only (corpus is embedded once and shipped pre-computed). load = model init.
Size
model download at the listed precision (int8 ≈ ¼ of fp32) + the vector index.
